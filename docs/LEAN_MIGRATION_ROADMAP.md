# 간편하고 근거 있는 AWS 설계·온프레미스 이전 — MVP 우선 로드맵

> **제품 목표:** 사용자가 GitHub 프로젝트를 처음 AWS에 배포하거나 기존 온프레미스 서비스의 AWS 이전을 검토할 때, **3단계 안에 무엇을 바꿀지/왜 바꿀지/어떤 위험이 있는지** 알 수 있게 합니다.
>
> **상태:** 신규 2모드, 비기밀 Inventory/As-Is, Rehost/Replatform의 서버·선언 연결별 변경표를 구현했습니다. 외부 저장소에서 신규·이전 입력 없음·가상 Inventory 입력의 3경로를 실행하고 다운로드한 보고서를 브라우저로 검사했습니다. **도면 전체 수동 승인, 실제 서버 자동 진단 및 AWS 이전 실환경 검증은 완료되지 않았습니다.** 현재 제공하는 기능은 저장소 정적 분석 → AWS To-Be 참조 설계·선정 근거·보안·비용 입력 기반 보고서입니다. 이 문서의 완료 기준은 향후 개발 목표입니다.

## 핵심 사용자 경험: 3단계만

1. **준비:** 프로젝트 저장소에 예시 GitHub Actions Workflow 1개를 추가합니다. 초기 단계에서 별도 AWS 계정, 설치형 에이전트, 키 입력은 불필요합니다.
2. **목적 선택 및 분석:** Actions 수동 실행에서 `신규 AWS 서비스 구축` 또는 `기존 온프레미스에서 AWS 이전`을 선택합니다. 기존 환경 이전 시에는 **비기밀 최소 Inventory**를 선택적으로 첨부할 수 있습니다. 정보가 부족하면 '확인 필요'로 멈춥니다.
3. **결과 확인:** 다운로드한 `START-HERE.html`에서 **현재 파악된 사실 → AWS 제안/대안 → 변경사항/위험 및 다음 행동**을 확인합니다. 추가 데이터가 필요할 때만 요구사항을 보완하여 재분석합니다.

초기 설정에서 GitHub Workflow 복사는 필요합니다. **브라우저에서 저장소 URL을 입력하면 자동으로 읽는 SaaS나 GitHub App 원클릭 설치 기능은 현재 제공하지 않습니다.**

## 최소 입력 원칙

- 처음 실행할 때 필수 선택은 **분석 목적 1개**. 대상 저장소는 Actions가 체크아웃하므로 별도 GitHub Token이나 URL을 묻지 않습니다.
- 2가지 실행 모드: `new_aws` / `migrate_onprem`.
- 온프레미스 이전은 구성정보가 없더라도 '추가 입력 필요' 보고서는 생성하되 **기존 서버/DB·네트워크를 추측하여 이전 완료 가능이라고 판단하지 않습니다**.
- 이전 Inventory 입력은 소수 호스트·DB·대외 접근·자원(대략적 CPU/RAM/스토리지)·운영 목표 등으로 **최소화**합니다. 세부 설계 필드, AWS 단가/SKU, IAM/SG는 기본적으로 요구하지 않습니다.
- 요구사항 질문은 처음에는 **최대 5가지 핵심 확인사항만 노출**하고 나머지 기술 항목은 '추가 검토'에 접습니다. 임의의 기본값을 사용자 확정 사항처럼 표기하지 않습니다.

## 간결한 출력 원칙

**비개발자 보고서(한 장, 핵심 영역 4개)**

| 영역 | 무엇을 보여주나 | 필수 신뢰성 표기 |
| --- | --- | --- |
| ① 현재 시스템(As-Is) | 코드에서 확인한 구조와 사용자가 입력한 현재 서버/DB/네트워크 | 코드 관측 / 사용자 입력 / 미확인 |
| ② 제안 아키텍처(To-Be) | AWS 권장 참조안과 **최대 2개 주요 대안** | 아직 구축·검증하지 않은 설계안 |
| ③ 바뀌는 점·리스크 | 유지/이전/변경/삭제 후보, 다운타임/DB·보안/외부 연동 확인 | 근거와 조치 주체; 미확인 시 차단 |
| ④ 다음 행동 | 확인 질문 최대 5개, 수동 재분석 경로 | 인증·승인·배포 자동 수행 없음 |

비용·용량 상세는 근거가 있을 때만 섹션을 펼쳐 보여주며, 단가/사용량 없으면 **미산정**입니다. 원본 AST·JSON·중간 단계 파일은 개발자용 Artifact에 유지하되 첫 화면에는 노출을 최소화합니다.

**근거 표시**는 하나의 일관된 계약을 사용합니다: `관측된 코드/설정`, `사용자 명시/자체 신고`, `참조 설계 가정`, `미확인`, `검증 결과`. 모델 추정 점수나 의미 없는 '신뢰도 93%'를 새로 만들지 않습니다. 추천 이유는 반드시 확인 가능한 요구조건/근거 및 불확실성을 참조하도록 합니다.

## MVP 출시 검수 기준

- **초보자 경로:** 기존 프로젝트 소유자가 예제 Workflow 한 파일을 복사하고 GitHub Actions에서 분석 목적을 고른 후 HTML을 열 수 있어야 합니다. 추가 설정은 선택입니다.
- **정확성:** 코드에 DB 라이브러리가 있다는 이유로 DB 서버 위치/네트워크/데이터 크기를 추측하지 않습니다. As-Is 관측과 AWS To-Be 제안/사람 검증을 뚜렷이 나눕니다.
- **안전성:** AWS 자격증명·원본 로그·IP·계정 정보의 중앙 수집 없음. 기본 외부 AI/실시간 가격 API 호출 없음. AWS 자원 생성/변경/삭제 불가.
- **결과 완결성:** 무엇을 선택했고 **왜**, 현재 시스템에서 무엇이 바뀌며, 확인하지 못한 항목과 담당자가 무엇인지까지 근거 링크가 존재합니다.
- **품질:** 신규/이전 대표 시나리오, 누락 입력, 데이터베이스 호환·민감 데이터/복구 충돌, HTML·SVG·PNG 시각 QA를 통과해야 기능 완료로 표시합니다.
- **보수적 권고:** 정보 부족 시 `확인 필요`를 반환하며, AWS 비용/성능/보안·마이그레이션 가능성·다운타임에 대한 허위 통과/완료 판정을 하지 않습니다.

## MVP에서 하지 않을 것

- 공개 저장소 URL만 입력하면 동작하는 별도 클라우드 SaaS, 필수 회원가입/결제, 상시 에이전트
- 온프레미스 서버에 대한 자동 SSH 접속 또는 관리자/DB 비밀번호 수집
- AWS 계정의 자동 리소스 변경, 데이터 복제/마이그레이션, 비용·SLA 자동 보증
- 사전 측정 없이 인스턴스 수/원가/다운타임을 임의 추산하거나 '정확도' 점수를 근거 없이 제시

**우선순위 원칙: 사용자 시작이 쉬운가 → 현재 상태에 근거가 있는가 → AWS 전환의 결정에 도움 되는가 → 실제로 검증했는가.** 기능 수보다 판단 신뢰성을 우선합니다.
